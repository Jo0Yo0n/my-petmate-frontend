# 프론트 개발 규칙

## 작업 범위와 협업

- 사용자는 백엔드 개발 경험이 있고 프론트는 처음이다. 목표는 AI 작업물을 이해하고 검증하며 유지보수할 수 있게 하는 것이다.
- AI가 합의한 범위의 코드·테스트·설정 작성과 실행 가능한 검증을 수행한다. 기기 조작·계정 설정이 필요하면 사용자가 해야 할 절차와 성공 확인 방법을 안내한다.
- [현재 단계](frontend-mvp-plan.md#현재-위치)를 확인하고 해당 상세 계획에 따라 한 번에 실행·확인 가능한 작은 단위를 진행한다. F0·F1 작업은 F0·F1 구현 계획을 먼저 읽는다. 각 단위 검증·설명 뒤 멈춰 사용자가 질문할 수 있게 한다. 함수·파일마다 승인을 받지 않는다.
- 중요한 계약·보안 정책·범위·기술 선택 변경은 문제·근거·대안·권장안을 먼저 설명하고 결정한다. 이미 채택된 결정은 다시 승인받지 않는다.
- 백엔드 계약은 읽기만 한다. 충돌과 변경 필요성은 보고하고 명시적 승인 없이 수정하지 않는다. 기존 미커밋 변경을 보존하고 관련 없는 수정·커밋·설치·배포를 하지 않는다.

## 설계와 코드

- Make it work → Make it correct → Measure → Make it better 순서로 진행한다. 확인된 문제가 있을 때만 개선한다.
- KISS·YAGNI·DRY를 따른다. 보안, 응집도·결합도, 데이터 정합성, 테스트 가능성은 기본 설계에 포함한다. 미래 확장만을 위한 인터페이스·범용 계층은 만들지 않는다.
- 설계 판단에서는 확장성·고가용성·부하분산·부분 실패·일관성·멱등성·관측성이 현재 동작에 미치는 영향을 확인한다. 클라이언트에 서버 인프라 책임을 추가하지 않는다.
- TypeScript strict를 기본으로 한다. 실제 파일 구조·버전·명령은 앱을 생성한 뒤 기록한다. 아직 없는 구조를 확정된 구현처럼 문서화하지 않는다.
- 일반 React Native 컴포넌트와 React 기본 상태 기능으로 시작한다. 상태·폼·UI 라이브러리를 추가하기 전 실제 기능 부족, 기존 도구로 처리하는 안, 도입 비용을 설명한다.
- 로컬 UI 상태·인증 상태·서버 데이터의 책임을 구분한다. 같은 사용자 데이터를 여러 상태 저장소에 중복 관리하지 않는다.
- 비동기 요청은 진행·성공·실패를 화면에 반영한다. 화면의 중복 제출 방지는 서버의 유일성·인가·트랜잭션을 대체하지 않는다.
- 인증·재시도 정책은 [인증 흐름](auth-flow.md)을 따른다. 비밀번호·토큰·민감한 응답은 코드·로그·오류 화면·테스트 보고서에 노출하지 않는다. 관측은 요청 경로·상태·code·requestId 등 필요한 범위로 제한한다.
- 명확한 코드는 주석으로 반복하지 않는다. 설계 이유·주의할 비동기 동작에만 주석을 남긴다.

## 검증

- 변경에 맞는 의미 있는 검증을 수행한다. 단순 문서 변경에 앱 테스트나 구현을 그대로 복사하는 테스트를 추가하지 않는다.
- 문서는 로컬 링크·앵커·기준 문서와의 일치·변경 범위·공백 오류를 확인한다.
- 앱 생성 이후 기본 검사 목표는 lint·typecheck·Jest 테스트다. 구체적인 스크립트는 실제 설정 후 README에 기록한다. 현재는 실행 가능한 npm 스크립트가 없다.
- 테스트는 사용자에게 보이는 동작과 중요한 실패·동시성 경로를 검증한다. snapshot만으로 동작을 확인하지 않는다.
- Playwright API 검증·RN 로직/화면 검증·iOS 실행 검증을 구분한다. 범위와 도구의 차이는 [가이드](frontend-guide.md#테스트의-층), M1 항목은 [인증 검증](auth-flow.md#검증-기준)을 따른다.
- 성공한 검사와 미실행 검사를 구분한다. 서버 체크리스트의 완료 기록을 이번에 재실행한 결과처럼 보고하지 않는다. 상태 표시는 실제 완료·검증 후에만 갱신한다.

## 단위 종료 시 설명

1. 현재 위치, 무엇을 만들었고 왜 필요한지.
2. 주요 파일의 역할·링크와 시작해서 읽을 파일.
3. 사용자 행동 → 화면 상태 → API 요청 → 응답 → 화면 변경 흐름. API가 없는 단위는 그 사실을 밝힌다.
4. 실제 코드에 새로 등장한 JavaScript/TypeScript·React·React Native/Expo 개념.
5. 실행한 검증과 사용자가 직접 확인할 절차.
6. 남은 제한과 다음 작업.

모든 줄을 설명하거나 코드 전체를 채팅에 반복하지 않는다. backend의 요청·응답·상태·동시성에 비유할 수 있지만 다른 개념을 동일하다고 설명하지 않는다. 별도 장기 강의로 확대하지 않는다.

## Git과 PR

- 사용자 요청 없이 커밋·push·PR 생성은 하지 않는다. 커밋 메시지·type·단위·사전 확인은 [커밋 규칙](git-conventions.md#커밋-규칙)을 따른다.
- PR은 [저장소 템플릿](../.github/pull_request_template.md)을 사용한다.
- 아직 확인·결정할 정책·의존성 항목은 [미결정 사항](decisions.md)에 남긴다. 확정되면 결과와 필요한 이유를 담당 문서에 반영하고 목록에서 제거한다. 규칙 원본을 여러 문서에 복사하지 않는다.
