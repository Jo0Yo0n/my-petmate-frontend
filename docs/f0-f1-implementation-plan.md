# F0·F1 구현 계획

이 문서는 F0·F1의 작은 구현 단위·완료 판정과 현재 검증 상태를 관리한다. 전체 범위·순서·단계별 상태는 [공통 MVP 계획](frontend-mvp-plan.md)을 따른다. 인증 정책과 상세 테스트는 인증
흐름, 단위별 설명·검증 절차는 개발 규칙을 따른다.

## 현재 작업 위치

현 기준 **0. 앱 구현 전 문서 정비 단위를 완료**했고 F0의 첫 화면 실행 기반을 준비 중이다. F1 앱 구현은 시작하지 않았다. 문서·PNG가 존재하는 것을 앱 구현·기기 검증 완료로 취급하지 않는다.

- 백엔드의 단계 상태는 [백엔드 계획](../../my-petmate-server/docs/backend-mvp-plan.md#진행-현황), M1 구현·검증 상태와
  게이트는 [M1 체크리스트](../../my-petmate-server/docs/m1-auth-contract-checklist.md)를 확인한다.
- Expo 앱의 최소 시작 화면과 실행 설정을 준비 중이다. 화면 구성은 [HTML/CSS 원본](design-assets/editable-wireframes/README.md), 시각
  규칙은 [Sunshine](ui-foundation.md)을 확인한다. Sunshine은 F1 전체 화면·탭 셸과 기존 F3 추천 목록·상세·F5 채팅 (F6 약속 카드)에 적용한다.
- 초기 실행 기본안은 로컬 Node 26·npm, SDK 57·iOS Simulator이며 생성 직전에 공식 지원 상태를 재확인한다. 개발 빌드는 Xcode로 로컬에서 생성한다. 패키지 조합은 설치·검증 후
  기록한다.
- 현재 실행 단위는 **1. 첫 iOS 화면**이다. 완료 기준은 아직 충족되지 않았다.

구현 단위별 상태와 완료 판정에 필요한 근거는 이 문서에서 현재 상태로 관리한다. 단계별 상태는 공통 MVP 계획에서 관리하며, 상세 작업이 검증·설명까지 끝났을 때만 갱신한다.

## F0→F1 작은 구현 단위

각 단위를 검증한 뒤 결과·파일·실행 흐름·새 개념·직접 확인 방법·제한을 설명하고 멈춘다.

| 단위               | 상태    | 실행·확인 결과와 검증                                                                                      | 이해 목표                                |
|--------------------|---------|------------------------------------------------------------------------------------------------------------|------------------------------------------|
| 0. 문서 기준 정비  | 완료    | 링크·계약 일치·결정 상태·변경 범위 확인. 앱·서버 미변경                                                    | 현재 위치, 자료별 책임, 왜 결정했는가    |
| 1. 첫 iOS 화면     | 진행 중 | 환경·SDK 재확인, 최소 앱 생성, iOS Simulator 첫 화면과 문구 수정 반영                                      | 컴포넌트·JSX·props·렌더링·시작 파일      |
| 2. 이동·입력       | 예정    | 로그인↔회원가입 이동, 입력·오류·제출 중 표현, 키보드·스크롤 확인. 실제 인증 전 보호 화면을 열지 않음       | state·hook·라우팅과 화면 갱신            |
| 3. API 경계        | 예정    | 실제 /me 미인증 응답 표시, 타입 생성·ProblemDetail 파서 검증. 로그에 토큰 노출 없음                        | API 환경·fetch·HTTP/통신 오류·requestId  |
| 4. 로그인·로그아웃 | 예정    | 실제 로그인→내 정보→로그아웃, 중복 제출·보호 경로 확인. 우선 실행 중 세션만 보장하고 재시작 유지 제한 명시 | 입력→요청→인증 상태→화면 전환            |
| 5. 세션 복원       | 예정    | SecureStore 저장·재시작·refresh·/me, 읽기/쓰기/삭제·통신/인증 실패 구분                                    | 메모리와 영속 저장, effect·복원 중 화면  |
| 6. 자동 갱신       | 예정    | 동시·늦은 만료 응답, refresh 공유, 재시도 상한, 응답 유실, 로그아웃 중 늦은 요청·저장 검증                 | Promise·동시성·부분 실패·세션 경계       |
| 7. 회원가입        | 예정    | 유형별 가입·찾기 상태·필드 오류·중복 email·가입 응답 유실·중복 제출                                        | 조건부 입력과 클라이언트/서버 validation |
| 8. 내 정보 수정    | 예정    | 유형·찾기 상태 수정, 최초 성별·보존·변경 거부·409·재조회 확인                                              | 서버 응답을 원본으로 화면 상태 갱신      |
| 9. 탈퇴·상태 안내  | 예정    | 탈퇴 확인·성공/불명확 결과, 정지·탈퇴 거부, 기기 정리·로그인 복귀 확인                                     | 파괴적 행동·계정 상태·권한 경계          |
| 10. F1 통합 검증   | 예정    | M1 프론트 게이트, RN 테스트, 시뮬레이터의 로컬 development build 저장·권한·재시작 확인                     | 검사 층·증거·남은 제한 파악              |

F0는 1~3의 실행 기반·입력/상태·API 환경·기본 검증을 준비한다. F1은 4~10에서 M1과 연결한다. 4의 메모리 세션은 중간 결과이며 최종 F1 완료가 아니다. 전체 MVP의 탭 구조는 셸까지만 준비하고
F1에서 아직 없는 반려견 API를 호출하거나 미구현 상태를 ‘등록 반려견 없음’으로 표시하지 않는다.

### 단위별 작업 체크리스트

아래 체크리스트는 위 표의 실행 순서를 구체화한다. 예정 작업은 모두 미완료로 두며, 구현·검증 증거를 확인한 항목만 체크한다. 파일명·패키지 버전·명령은 실제 구성 뒤 기록한다. 한 단위가 한 번에 확인하기에 크면
번호 순서대로 작업을 나누고, 실행 가능한 결과에서 설명 후 멈춘다.

#### 0. 문서 기준 정비 — 완료한 범위

완료 범위는 현재 위치·자료별 책임·계약과 링크 정합성 점검이다. 앱 구현과 iPhone 실행은 아직 완료되지 않았다.

#### 1. 첫 iOS 화면

- [ ] 1-1. 로컬 Node·npm·Xcode와 iOS Simulator 런타임을 확인한다. 생성 직전 공식 지원 문서로 SDK·Node 호환성을 재확인하고 실제 사용 버전을 기록한다.
- [ ] 1-2. 기존 문서·에셋·미커밋 변경을 보존하며 최소 Expo·TypeScript strict 앱을 생성한다. Expo Router 시작 파일과 기본 화면을 확인하고 불필요한 예제 화면을 정리한다.
- [ ] 1-3. 한국어 문구가 있는 최소 화면을 만들고 밝은 모드·Safe Area를 적용한다. 인증·API·전체 탭 기능은 이 단계에 묶지 않는다.
- [ ] 1-4. iOS Simulator에서 앱을 열고 문구 변경이 반영되는지 확인한다. 연결 실패가 있으면 개발 서버 접근과 앱 실행 문제를 구분해 해결한다.
- [ ] 1-5. 실행·lint·typecheck·Jest의 최소 설정을 마련하고, 실제로 동작하는 명령과 시작 파일을 README에 기록한다. Jest는 이후 로직 검증에 사용할 환경까지만 준비한다.

완료 기준: iOS Simulator에서 첫 화면과 문구 수정 반영을 확인하고, 완료 판정에 필요한 검증 상태와 근거를 유지한다. 실제 iPhone 검증은 F8에서 수행한다. 컴포넌트·JSX·props·렌더링을 실제
시작 파일과 연결해 설명한다.

#### 2. 이동·입력

- [ ] 2-1. 화면 정의와 현재 Sunshine HTML/CSS를 대조해 로그인·회원가입 경로를 구성한다. HTML을 RN 화면으로 옮길 때 입력·배치·접근성 속성의 차이를 확인한다.
- [ ] 2-2. 로그인 이메일·비밀번호와 가입 기본 필드를 React state로 관리한다. 비밀번호 확인은 가입 화면에서만 두고 원문 그대로 비교한다. 유형·개인 성별·찾기 상태는 미선택에서 시작한다.
- [ ] 2-3. 개인 선택 시 성별을 표시하고 커플·가족에서는 숨긴다. 필수 입력·비밀번호 확인 오류를 필드 가까이에 표시한다. 서버 계약의 세부 validation 연결은 3·7에서 마무리한다.
- [ ] 2-4. API 연결 전에는 제어된 화면 상태로 오류·제출 중 표현을 확인한다. 버튼과 키보드 제출은 같은 처리 경로를 사용하고, 모의 제출을 실제 가입·로그인 성공으로 표시하지 않는다.
- [ ] 2-5. 로그인↔가입 이동·뒤로 가기, Safe Area·키보드 회피·스크롤·입력 자동완성·접근 가능한 label을 iOS Simulator에서 확인한다. 비로그인 상태에서 보호 경로에 접근할 수 없게
  한다.
- [ ] 2-6. 조건부 성별·비밀번호 확인·이동·중복 제출 방지에 필요한 RN 화면 테스트를 추가한다.

완료 기준: 실제 인증 없이 두 폼을 이동·입력하고 필요한 상태를 확인할 수 있다. 입력 이벤트 → state 변경 → 재렌더링과 라우팅을 설명한다.

#### 3. API 경계

- [ ] 3-1. 실제 OpenAPI·오류 계약의 인증 경로·요청/응답·헤더를 확인한다. API 기본 URL을 환경 설정으로 분리하고 실행 환경에서 접근 가능한 주소를 사용한다. 앱에 포함되는 환경 값에 비밀을
  넣지 않는다.
- [ ] 3-2. OpenAPI에서 타입을 생성하는 최소 도구·명령을 구성한다. 실제 계약으로 재생성하고 typecheck를 통과시켜 수작업 타입과 계약이 갈라지지 않게 한다.
- [ ] 3-3. 작은 fetch 클라이언트에서 JSON 요청·성공 응답·본문 없는 성공 응답·HTTP 실패·통신 실패를 처리한다. 토큰 자동 갱신은 아직 추가하지 않는다.
- [ ] 3-4. ProblemDetail의 status·code·선택 fieldErrors·header/body requestId를 처리한다. status 불일치·잘못된 JSON·JSON이 아닌 장애 응답을
  구분하고 앱이 중단되지 않게 한다.
- [ ] 3-5. 실제 미인증 `GET /api/guardians/me`를 호출해 오류 안내와 요청 ID 처리를 확인한다. 진단용 호출은 인증 성공이나 보호 화면 접근으로 이어지지 않게 한다.
- [ ] 3-6. 실제 파서에 계약 오류·필드 오류·비정상 응답을 주는 테스트를 작성하고 `M1-REG-FE-01`의 증거를 기록한다. 로그·오류 화면에 비밀번호·토큰·민감한 응답이 없는지 확인한다.

완료 기준: 실제 미인증 응답을 안전하게 표시하고 타입 생성·파서 검증을 재현할 수 있다. HTTP 오류와 네트워크 오류, 컴파일 시 타입과 런타임 응답 검증의 차이를 설명한다.

#### 4. 로그인·로그아웃 — 실행 중 세션

- [ ] 4-1. 로그인 validation을 계약에 연결한다. 가입용 비밀번호 복잡도 조건을 로그인에 재적용하거나 비밀번호를 trim하지 않는다.
- [ ] 4-2. 로그인 → 메모리의 토큰·Guardian 반영 → 내 정보 표시 흐름을 연결한다. 이 단위에서는 refresh token도 메모리에만 두며 앱 재시작 유지가 안 된다는 제한을 명시한다.
- [ ] 4-3. 인증 담당 코드가 세션을 소유하고 화면은 직접 토큰을 다루지 않게 한다. 인증 여부에 따라 보호 경로와 뒤로 가기를 제어한다.
- [ ] 4-4. 내 정보 진입에서 실제 `/me`를 조회하고 로딩·실패·재시도를 표시한다. 전체 탭은 셸까지만 준비하고 F2 API나 가짜 반려견 빈 결과를 연결하지 않는다.
- [ ] 4-5. 로그아웃 확인 → 현재 refresh token 폐기 시도 → 메모리·개인 데이터 정리 → 로그인 복귀를 구현한다. 서버 폐기 실패와 로컬 종료 결과를 구분한다.
- [ ] 4-6. 자격 증명 오류·통신 실패·중복 제출·비로그인 보호 경로·로그아웃 후 뒤로 가기를 테스트한다. 종료된 세션의 늦은 로그인·조회 응답이 화면을 복원하지 않는지도 확인한다.

완료 기준: 실제 로그인·내 정보 조회·로그아웃을 한 실행에서 확인한다. 영속 저장·자동 갱신이 아직 없는 제한을 현재 상태에 반영한다.

#### 5. 세션 복원 — SecureStore

- [ ] 5-1. SecureStore를 구성하고 refresh token만 영속 저장한다. access token·비밀번호·Guardian을 별도 영속 저장하지 않는다.
- [ ] 5-2. 로그인 성공 시 refresh 저장이 끝난 뒤 인증 완료로 전환한다. 저장 실패면 보호 화면 진입을 막고 재로그인 안내를 제공한다.
- [ ] 5-3. 앱 시작을 복원 중 → 저장 값 읽기 → refresh → 새 refresh 저장 → `/me` → 인증 완료로 연결한다. 값 없음·읽기 실패·통신 실패·명시적 인증 거부를 구분한다.
- [ ] 5-4. 복원 중 로그인·보호 화면이 잠깐 나타나지 않게 하고, `/me` 일시 실패에는 사용자 정보를 추측하지 않고 재시도를 제공한다. effect 재실행으로 복원을 중복 요청하지 않게 한다.
- [ ] 5-5. 로그아웃에 저장 값 삭제를 연결한다. 삭제 실패면 별도 재시도를 제공하고 현재 실행의 자동 복원을 막으며 기기 로그아웃 완료로 표시하지 않는다.
- [ ] 5-6. 읽기·쓰기·삭제 실패와 복원 중 `/me` 실패를 제어한 테스트를 작성한다. iOS Simulator에서 저장·강제 종료·재시작·삭제를 확인한다.

완료 기준: 재시작 후 복원이 되고 저장소·통신·인증 실패별 화면을 확인한다. 메모리와 영속 저장의 수명, effect와 비동기 복원을 설명한다. 시뮬레이터의 우리 development build 검증은 10에서
마무리하고 실제 iPhone 검증은 F8에서 수행한다.

#### 6. 자동 갱신 — 동시성·부분 실패

- [ ] 6-1. 인증 흐름의 code별 분기를 API 클라이언트에 연결한다. `AUTH_TOKEN_EXPIRED`일 때만 자동 갱신하고 공개 인증 요청에는 재귀 적용하지 않는다.
- [ ] 6-2. 동시에 만료된 요청이 refresh Promise 하나를 공유하게 한다. 갱신 후 도착한 이전 토큰의 만료 응답은 현재 토큰을 사용하며 원 요청별 재시도를 최대 한 번으로 제한한다.
- [ ] 6-3. 갱신된 refresh의 저장 성공을 확인하고 세션을 반영한다. 응답 유실·통신/5xx·저장 실패에서 무조건 반복하지 않고 재시도·재로그인 경로를 제공한다.
- [ ] 6-4. 로그아웃·계정 전환 시 종료된 세션의 늦은 요청·갱신·저장이 토큰·Guardian·보호 화면을 되살리지 못하게 한다. 갱신 저장과 삭제의 순서를 조정하고 로그아웃은 알고 있는 최신 refresh를
  사용한다.
- [ ] 6-5. 실제 인증 코드에 제어된 HTTP·저장 경계를 연결해 동시 만료·늦은 만료·재시도 상한·만료 외 401·회전 응답 유실·종료 중 저장 경합을 검증한다. `M1-REG-FE-02` 증거를 기록한다.

완료 기준: 정상 갱신과 중요한 실패·경합 테스트가 통과한다. Promise 공유와 서버 잠금의 차이, 서버 회전과 기기 저장이 하나의 트랜잭션이 아닌 이유를 설명한다.

#### 7. 회원가입

- [ ] 7-1. 가입 직전 실제 서버의 최신 계약·구현 준비 상태를 확인한다. 닉네임·유형·개인 성별·찾기 상태·활동 지역·시간의 요청과 응답이 일치하는지 대조하며 서버 변경 대기를 앱 모의 성공으로 대체하지
  않는다.
- [ ] 7-2. 가입 전 공개 지역 카탈로그와 지역·요일별 시간대 입력을 연결한다. 지역/시간 누락·중복·상한·시간 역전/겹침을 검증하고 가입 필드의 필수값·길이·email 정규화·비밀번호 조건을 OpenAPI에
  연결한다. 비밀번호 확인은 로컬에서만 비교하고 요청·저장·로그에서 제외한다.
- [ ] 7-3. 개인·커플·가족 요청을 구분한다. 개인은 성별 필수, 커플·가족은 생략하며 닉네임·찾기 상태·활동 지역·시간대를 계약대로 전송한다.
- [ ] 7-4. 가입 성공을 기존 저장·인증 완료 흐름에 연결한다. 버튼·키보드의 중복 제출을 막고 제출 후 비밀번호 입력을 정리한다.
- [ ] 7-5. fieldErrors·중복 email을 해당 필드에 표시한다. 통신 실패로 가입 결과가 불명확하면 자동 재전송하지 않고 로그인으로 확인하는 경로를 제공한다.
- [ ] 7-6. 유형별 성공·필수 선택 누락·비밀번호 불일치·중복 email·응답 유실·저장 실패를 검증하고 iOS Simulator에서 긴 폼·키보드 동작을 확인한다.

완료 기준: 유형별 실제 가입과 실패 안내를 확인한다. 클라이언트 validation은 사용자 피드백이며 서버의 검증·유일성 보장을 대체하지 않음을 설명한다.

#### 8. 내 정보 수정

- [ ] 8-1. 실제 `/me`로 닉네임·선택 사진·유형·성별·찾기 상태·활동 지역·시간대를 조회한다. 수정 진입 시 서버 값을 입력 초깃값으로 사용하고 취소하면 제출하지 않는다.
- [ ] 8-2. 닉네임·유형·찾기 상태·활동 지역·시간대 수정을 구현한다. 지역·시간 목록은 다른 수정값과 원자적으로 저장하며 취소하면 원본을 유지한다. PATCH도 유형별 필수값을 전송하고
  status·email·비밀번호를 요청에 넣지 않는다.
- [ ] 8-3. 성별 미설정 계정의 최초 개인 전환에만 선택을 받는다. 기존 성별은 읽기 전용·동일 값 전송으로 처리하고 커플·가족 수정에서는 생략한다. 최초 설정 안내를 제출 전에 표시한다.
- [ ] 8-4. 선택 사진의 실제 업로드 계약·제한·서버 준비 상태를 확인하고 사진 선택·업로드·조회 반영을 연결한다. 필요한 이미지 처리·권한 도구는 이 작업에서 확인하며 F2 사진 처리 구상을 그대로 확정하지
  않는다.
- [ ] 8-5. 사진 업로드와 정보 수정을 별도 요청으로 처리하고 일부만 성공하면 결과를 구분한다. 취소·실패 시 유지 가능한 입력을 유지하며 서버에서 확인한 값으로 현재 Guardian을 갱신한다.
- [ ] 8-6. `STATE_CONFLICT`는 안내·재조회로 최신 값을 확인하고 자동 덮어쓰지 않는다. 최초 성별·유형 전환 후 보존·변경 거부·409·닉네임 오류·사진 실패·부분 성공을 검증한다.

완료 기준: 조회·수정·취소·재조회와 선택 사진의 성공/실패를 확인한다. 편집 중 로컬 상태와 서버 원본의 차이, 충돌 시 재조회가 필요한 이유를 설명한다.

#### 9. 탈퇴·상태 안내

- [ ] 9-1. 내 정보에서 탈퇴 확인을 열고 취소·확인을 구분한다. 복구 미지원·계정 접근 종료를 안내하고 즉시 물리 삭제를 약속하지 않는다.
- [ ] 9-2. 확인 후 body 없이 탈퇴 API를 한 번 제출하고 본문 없는 성공 응답을 처리한다. 성공하면 메모리·저장 세션·개인 데이터를 정리하고 로그인으로 복귀한다.
- [ ] 9-3. 통신 실패·5xx는 결과 불명확으로 안내한다. 확인·재시도 경로를 제공하고 기존 access token 재시도에서 `ACCOUNT_WITHDRAWN`을 받으면 상태 안내·세션 정리를 수행한다.
- [ ] 9-4. 로그인·복원·보호 API의 `ACCOUNT_RESTRICTED`·`ACCOUNT_WITHDRAWN`을 보호 영역 밖 안내로 연결한다. 일반 `FORBIDDEN`과 구분하고 제한 사유·기간을
  추측하지 않는다.
- [ ] 9-5. 탈퇴 취소·성공·응답 유실·중복 제출·기기 삭제 실패·상태별 거부·늦은 응답·뒤로 가기 차단을 검증한다. 폐기 refresh가 `AUTH_REFRESH_INVALID`를 반환하는 경로도 확인한다.

완료 기준: 탈퇴 완료와 불명확 결과가 구분되고 정지·탈퇴 계정이 보호 화면에 남지 않는다. 계정 상태·인증·인가와 파괴적 요청의 부분 실패를 설명한다.

#### 10. F1 통합 검증

- [ ] 10-1. 실제 OpenAPI로 타입을 재생성하고 lint·typecheck·Jest·관련 RN 화면 테스트를 실행한다. 3·6의 M1 증거가 최종 코드에도 유효한지 확인한다.
- [ ] 10-2. 프론트 저장소의 Playwright APIRequestContext로 실제 signup → GET/PATCH me → refresh → 이전 refresh 거부 → logout을 검증한다.
  status·body·Content-Type·요청 ID를 확인하고 `M1-REG-FE-03` 증거를 기록한다.
- [ ] 10-3. 로그인·가입·복원·수정·로그아웃·탈퇴 흐름과 인증/통신/저장 실패를 통합 확인한다. 실제 인증 코드 테스트와 서버 API 테스트의 증거를 구분한다.
- [ ] 10-4. Xcode로 로컬 생성한 우리 development build를 iOS Simulator에서 검증한다. Xcode·시뮬레이터 설정을 확인하고 SecureStore 저장·삭제·강제
  종료·재시작·실제 백엔드 연결·사진 권한을 점검한다.
- [ ] 10-5. iOS Simulator에서 작은 화면·키보드·자동완성·큰 글씨·VoiceOver·Safe Area·긴 오류·재시도를 확인한다. 실제 iPhone 검증은 F8에서 수행한다.
- [ ] 10-6. 완료 판정에 필요한 시뮬레이터 검증 상태·근거와 실제 기기 미검증 등 남은 제한을 이 문서에 반영한다. 사용자 직접 확인과 단위 설명까지 끝난 범위만 공통 MVP 계획에 반영한다. 백엔드
  체크리스트 변경과 F2 착수는 별도 요청을 따른다.

완료 기준: 아래 F0·F1 완료 판정과 인증 검증 항목에 증거가 연결된다. 미실행 검사가 남으면 F1 완료로 표시하지 않고 남은 확인을 명시한다.

### 검증 상태 관리

단위별 완료 상태와 남은 제한을 현재 상태로 갱신한다. 기기 확인과 M1 게이트처럼 완료 판정에 필요한 항목은 확인 주체·환경과 재확인할 수 있는 근거를 간결하게 유지한다. 이전 실행 결과는 누적하지 않는다.

### F0·F1 완료 판정

- 실제 구성 후 lint·typecheck·Jest와 관련 화면 테스트를 실행한다. 명령은 README에 실제 설정을 기록한 뒤 사용한다. 타입 생성은 실제 OpenAPI로 재현 가능하게 검증한다.
- F1의 상세 실패·동시성·기기 항목과 M1-REG-FE-01~03의 증거는 [인증 검증](auth-flow.md#검증-기준)에 맞춰 기록한다. Playwright는 API 검증에 사용하며 웹 앱을 추가하지
  않는다.
- iOS Simulator에서 작은 화면·키보드·자동완성·큰 글씨·VoiceOver·실제 백엔드 연결을 확인한다. 실제 iPhone 확인은 F8에서 수행한다. 다크 모드는 검증 범위에서 제외한다.
- 시뮬레이터 검증의 현재 상태·확인 주체·환경과 실제 기기 미검증 항목을 유지한다. 수동 확인이나 사용자 이해가 끝났다고 AI가 임의로 판정하지 않는다.
