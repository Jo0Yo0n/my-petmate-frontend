# F1 인증 흐름

앱 구현 전의 클라이언트 설계

2026-10-22 승인 계약: `discoveryStatus: searching | paused`를 사용한다. 백엔드의 기존 `identityVisibility` 구현은 교체·마이그레이션·재검증 대기이며 현재 서버와 연결 검증을 완료한 것으로 간주하지 않는다.

## 기준과 책임

- [OpenAPI](../../my-petmate-server/docs/openapi.yaml): `info.x-token-policy`, `info.x-email-policy`, `/api/auth/*`, `/api/guardians/me`, `/api/guardians/me/withdraw`, `Guardian*`·`*SignupRequest`·`LoginRequest` 스키마.
- [오류 계약](../../my-petmate-server/docs/error-response.md): 오류 본문·요청 ID·계정 상태 오류의 검증 순서.
- [M1 게이트](../../my-petmate-server/docs/m1-auth-contract-checklist.md)와 [상세 테스트](../../my-petmate-server/docs/m1-test-cases-detail.md): 완료 판정과 프론트 검증 항목.

TTL·패턴·응답 필드 목록은 이 문서에 복사하지 않는다. 아래는 그 계약을 앱 동작으로 연결한 설계다. 서버가 인증·인가·상태·정합성을 보장하고 앱의 보호 경로는 화면 노출을 제어한다.

## 저장과 인증 상태

| 값                      | 보관                     | 사용                                            |
|-------------------------|--------------------------|-------------------------------------------------|
| access token            | 메모리                   | 보호 API의 Bearer 인증                          |
| refresh token           | SecureStore              | 재시작 복원·갱신·로그아웃. 회전 때 교체         |
| 비밀번호                | 입력·요청 처리 중 메모리 | 저장·로그 기록 금지. 사용 후 폼 정리            |
| 현재 Guardian·인증 상태 | 인증 담당 코드           | 화면 진입·설정 표시. 서버 데이터 중복 보관 금지 |

화면은 토큰을 직접 읽거나 갱신하지 않는다. 작은 인증 담당 코드가 저장·복원·종료를 관리하고, API 클라이언트가 그 세션의 access token으로 요청한다. 범용 인증 프레임워크는 만들지 않는다.

화면은 최소한 복원 중, 비로그인, 인증 완료, 복원 재시도 필요 상태를 구분한다. 정지·탈퇴 안내는 보호 영역 밖에서 보인다. 구현에서 enum·파일 이름은 이 책임을 표현하는 최소 구조로 정하고 실제 링크를 추가한다.

SecureStore 읽기·쓰기·삭제는 실패할 수 있다. 저장에 실패한 세션을 정상 복원 가능 상태로 표시하지 않는다. iOS Keychain은 재설치 후에도 값이 남을 수 있어 앱 삭제를 로그아웃으로 간주하지 않는다. 생체 인증 요구·별도 비밀번호 저장은 추가하지 않는다.

## 로그인과 회원가입

사용자 제출 → 로컬 validation → 제출 중 → API 요청 → 새 refresh token 저장 → access token·Guardian 반영 → 보호 화면 순서로 처리한다. 저장 실패면 성공 화면 진입을 막고 복구·재로그인을 안내한다. 토큰을 출력해서 확인하지 않는다.

- 개인·커플·가족을 제공한다. 개인은 여성·남성 중 하나가 필수다. 커플·가족은 성별 입력을 숨기고 요청에서 생략한다. 비밀번호 확인은 필수 입력이며 원문과 정확히 비교한다. 미입력·불일치하면 요청하지 않고 확인 필드 아래에 안내한다. 공백 제거 등 정규화는 하지 않으며 확인 값은 API 전송·영속 저장·로그에 포함하지 않는다.
- email 정규화와 가입 비밀번호 조건은 OpenAPI를 따른다. 로그인에 가입용 복잡도 조건을 다시 적용하지 않는다. 비밀번호는 임의 trim·소문자 변환을 하지 않는다.
- 찾기 상태를 명확히 입력받는다. 유형·개인 성별·찾기 상태는 모두 미선택으로 시작하고 제출 전에 필수 선택한다. 찾는 중에는 추천·선제 관심을 사용할 수 있고, 쉬는 중에는 기존 받은 관심 응답·매칭·채팅·약속을 유지한다.
- `fieldErrors`의 field·reason은 해당 입력에 연결하고, 중복 email은 email 필드에 표시한다. 로그인 자격 증명 오류는 어떤 값이 틀렸는지 구분하지 않는다.
- 버튼 탭과 키보드 제출이 같은 진행 상태를 사용해 중복 제출을 막는다. 가입·로그인 요청의 통신 실패를 자동 재전송하지 않는다. 가입 응답이 유실되면 성공 여부가 불명확하다고 안내하고 로그인으로 확인할 수 있게 한다.

## 앱 시작과 복원

```text
앱 시작 → 복원 중 화면 → SecureStore 읽기
  값 없음 → 로그인
  읽기 실패 → 저장소 오류·재시도 (보호 화면 진입 금지)
  값 있음 → refresh → 새 refresh 저장 → access token 반영 → GET me → 인증 완료
```

- 복원 전에 로그인 화면·보호 화면을 잠깐 표시하지 않는다.
- refresh 응답은 토큰 쌍이므로 `/me`로 현재 Guardian을 조회한다.
- `/me`의 일시적 실패는 재시도 상태로 두며 서버 사용자 정보를 추측하지 않는다. 명시적인 인증 거부는 아래 오류 분기를 따른다.
- refresh의 통신 장애·5xx만으로 저장된 토큰을 즉시 무효로 간주하지 않는다. 보호 화면을 열지 않고 재시도·재로그인 경로를 제공한다.
- effect 재실행이나 동시 호출로 시작 복원이 중복되지 않도록 같은 진행 중 복원·갱신을 공유한다.

## 자동 갱신과 오류 분기

| 응답                                       | 클라이언트 동작                                                              |
|--------------------------------------------|------------------------------------------------------------------------------|
| `AUTH_TOKEN_EXPIRED`                       | 공개 인증 요청을 제외한 원 요청에 대해 갱신 한 번, 원 요청 재시도 최대 한 번 |
| `AUTH_TOKEN_INVALID`                       | 자동 갱신 없이 세션 정리·로그인                                              |
| `AUTH_INVALID_CREDENTIALS`                 | 로그인 폼에 실패 표시. 자동 갱신 안 함                                       |
| `AUTH_REFRESH_INVALID`                     | 세션 정리·로그인                                                             |
| `ACCOUNT_RESTRICTED` / `ACCOUNT_WITHDRAWN` | 자동 갱신 없이 세션 정리·상태별 안내                                         |
| 일반 `FORBIDDEN`                           | 접근 거부 표시. 본인 계정 정지·탈퇴로 해석하지 않음                          |
| 통신 실패·5xx                              | 작업 실패·재시도 안내. 인증 무효로 단정하거나 무조건 재전송하지 않음         |

동시에 만료 응답을 받은 요청은 진행 중인 refresh Promise 하나를 공유한다. 이미 갱신된 뒤 도착한 이전 access token의 만료 응답은 현재 토큰으로 원 요청을 한 번 재시도하며 불필요한 추가 회전을 만들지 않는다. refresh·login·signup·logout 자체에 갱신을 재귀 적용하지 않는다.

로그아웃·계정 전환으로 종료된 세션의 늦은 응답은 토큰·사용자·보호 화면을 복원하지 못하게 한다. 진행 중 요청과 저장 작업의 완료 순서를 통제해 오래된 refresh 저장이 삭제 뒤 실행되지 않도록 한다. 이것은 앱 한 실행 내의 조정이며 서버의 DB 잠금과 같은 기능이 아니다.

HTTP status로 큰 범주를 판단하고 `code`로 구체적인 동작을 선택한다. detail 문자열 비교로 분기하지 않는다. `application/problem+json`, 선택적인 fieldErrors, header·body requestId를 처리하고 status 불일치·잘못된 응답은 계약 오류로 식별한다. JSON이 아닌 장애 응답도 앱 전체를 중단시키지 않도록 일반 오류로 다룬다.

### refresh 응답 유실

서버가 회전을 커밋한 뒤 응답이 유실되면 앱에는 이전 refresh token만 남을 수 있다. 서버 DB 커밋과 앱의 응답 수신·SecureStore 저장은 하나의 transaction이 아니다. 현재 계약은 회전된 이전 토큰의 재사용을 거부한다.

refresh를 무조건 자동 반복하지 않는다. 일시적 실패에는 재시도 UI를 제공하되, 복구 요청에서 무효가 확인되면 재로그인한다. 같은 응답을 다시 돌려주는 서버 복구 계약·재사용 유예·token family를 추가하지 않는다. 서버에서 성공했으나 새 토큰 저장에 실패한 경우에도 재로그인이 필요할 수 있음을 안내한다.

## 내 정보와 수정

- `/me`는 본인 전용 응답이다. 보존된 gender는 커플·가족 응답에도 들어올 수 있으며 미설정은 null이다. 상대 보호자 공개 정보와 혼동하지 않는다.
- 개인으로 처음 설정할 때 성별이 저장되고 이후 변경할 수 없다. 기존 값이 있으면 개인 입력은 읽기 전용으로 표시하고 동일 값을 전송한다. 커플·가족으로 전환해도 기존 성별은 지워지지 않는다.
- 커플·가족 수정에서는 성별을 생략한다. 미설정 계정이 처음 개인으로 바뀔 때만 선택한다. 최초 저장 이후 변경할 수 없음을 제출 전에 설명한다.
- PATCH라도 유형별 필수 필드를 모두 전송한다. 찾기 상태만 단독 전송하는 부분 수정으로 오해하지 않는다. status·email·비밀번호는 수정 요청에 넣지 않는다.
- 성공 응답으로 현재 Guardian을 갱신한다. `STATE_CONFLICT`는 안내와 재조회로 최신 상태를 확인하고 자동 덮어쓰지 않는다. 서버는 동시 최초 성별 설정도 보호한다.

## 로그아웃

1. 제출 중 상태로 전환하고 새 인증 요청·갱신을 막는다. 진행 중 회전·저장과의 경합을 정리한다.
2. 알고 있는 현재 refresh token으로 서버 폐기를 시도한다. refresh 성공 응답을 이미 받은 경우 최신 토큰을 대상으로 한다. 토큰이 없거나 읽지 못해도 기기 정리는 시도한다.
3. 서버 결과와 별개로 메모리·개인 데이터·기기 refresh token을 정리하고 보호 화면 접근을 막는다.
4. 서버 폐기 확인과 로컬 삭제 결과를 구분한다. 서버 미확인은 성공으로 기록하지 않으며 일반 안내를 표시한다. SecureStore 삭제 실패는 별도 오류와 삭제 재시도를 제공하고 현재 실행에서 자동 복원을 막는다. 삭제 전에 앱이 종료되면 토큰이 남아 재시작 시 복원될 수 있으므로 기기 로그아웃 완료라고 표시하지 않는다.

서버 logout은 멱등하지만 네트워크가 끊기면 서버 폐기를 보장할 수 없다. 영구 재시도 큐를 두지 않으며 복원·서버 상태가 불명확한 경우 서버 만료까지 자격 증명이 남을 수 있다. access token 즉시 블랙리스트·전체 기기 로그아웃은 현재 계약에 없다.

## 탈퇴와 계정 상태

- 설정에서 탈퇴 진입·확인을 제공한다. 복구 미지원과 계정 접근 종료를 설명하되 개인정보 즉시 물리 삭제를 약속하지 않는다.
- 확인 후 별도 탈퇴 API를 body 없이 호출한다. 성공은 body 없는 응답으로 처리하고 모든 로컬 세션·개인 데이터를 정리한다.
- 통신 실패·5xx이면 탈퇴 완료를 단정하지 않는다. 확인·재시도 경로를 제공한다. 유효한 기존 access token으로 재시도해 `ACCOUNT_WITHDRAWN`을 받으면 상태 안내와 세션 정리를 수행한다.
- 정지·탈퇴 계정은 로그인·갱신·모든 보호 API에서 거부된다. 보호 탭 안에 머물거나 내 반려견으로 이동시키지 않는다. 제한 사유·기간·해제 절차는 계약에 없어 만들어내지 않는다.
- 폐기된 refresh token은 먼저 `AUTH_REFRESH_INVALID`가 될 수 있다. 모든 탈퇴 복원 시도에서 반드시 `ACCOUNT_WITHDRAWN`을 받는다고 가정하지 않는다.

## 검증 기준

| 범위           | 검증                                                                                                                                                         |
|----------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `M1-REG-FE-01` | OpenAPI 타입 생성, 실제 오류 파서의 status·code·fieldErrors·requestId 처리, 계약 불일치 발견                                                                 |
| `M1-REG-FE-02` | 실제 인증 클라이언트에 제어된 HTTP 응답을 주어 동시 만료·늦은 만료 응답·갱신 한 번·원 요청별 재시도 한 번·만료 외 401 무갱신 검증                            |
| `M1-REG-FE-03` | 프론트 저장소의 Playwright APIRequestContext로 실제 signup → GET/PATCH me → refresh → 이전 refresh 거부 → logout 흐름. status·body·Content-Type·요청 ID 확인 |
| 화면           | 유형별 입력·보존 성별·필드 오류·중복 제출·상태 안내·탈퇴 확인·보호 경로 차단                                                                                 |
| 저장·부분 실패 | 읽기/쓰기/삭제 실패, 회전 응답 유실, `/me` 실패, 오프라인 로그아웃, 탈퇴 결과 불명확, 로그아웃·계정 전환 중 늦은 응답·저장                                   |
| iOS            | 실제 SecureStore 저장·복원·삭제와 앱 종료·재시작, 키보드·자동완성·작은 화면·큰 글씨·VoiceOver·LAN. Expo Go 확인 후 우리 development build에서도 확인         |

Jest 테스트는 실제 프론트 인증 코드를 실행하고 HTTP·저장 경계만 제어한다. Playwright API 테스트만으로 앱 인증 코드가 검증됐다고 판단하지 않는다. iOS 네이티브 화면을 Playwright가 직접 조작한다고 가정하거나 테스트만을 위해 웹 앱을 추가하지 않는다. 미검증 게이트·서버 마일스톤을 임의로 완료 처리하지 않는다.

## 닉네임·사진·사용자 안내

가입 시 닉네임을 필수로 입력하고 본인 정보 조회·수정에 사용한다. 사진은 선택이며 본인 사진 업로드 API와 프로필 수정은 별도 요청이다. 일부만 성공하면 완료 범위를 구분한다. 저장소 장애는 내부적으로 처리하고 독립 관리 화면·기술 문구 대신 해당 작업의 일반 실패·재시도 안내를 제공한다. 저장 실패 후 인증 완료나 삭제 실패 후 로그아웃 완료를 거짓으로 표시하지 않는다. 서버 구현·마이그레이션은 별도다.
